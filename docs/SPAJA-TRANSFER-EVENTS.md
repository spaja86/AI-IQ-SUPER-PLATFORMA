# SPAJA transfer event audit

User approved additive audit and stale-export prevention after #1319. PetljaResult gains optional transferEvents; SPAJA populates it in memory. Existing non-SPAJA results unchanged. Events include export/import/unavailable/invalidated, current segment index/loop, source segment/loop when known, numeric value, exported fields and import target or reason. Array records actual runtime events, not inferred plans. No timestamp/persistent audit/hash or authorization is claimed.

Import event emitted only after guard accepts the next child, immediately before application to its input. Export emitted only after completed child produces finite export. Failed child invalidates cached export even in direct-runtime fallback; next importing segment records unavailable and cannot consume a previously successful child result. This intentionally changes stale-export fallback behavior; old runtime tests remain green. Strict still halts. Existing workingInput state is not rolled back on invalidation: prior applied imports remain in that state; no claim of transactional rollback. Event export does not guarantee later consumption; unmatched exports may be intentionally unused at termination. Unavailable is lack of current export, not an exception.

VRH profile remains strict-only; fallback NOT enabled through dispatcher. No recursion, arbitrary graph, Java support, external storage or production changes. All 153 existing tests pass; new tests assert FOR→DOK provenance, stale export revocation (fallback result now 7), strict stop and guard-before-import. Existing SPAJA profile regression, targeted lint, isolated strict dispatcher typecheck and diff run separately. Full build/CI/Preview, JVM and every transfer combination unverified.

Review response schema consumers before merge: optional numeric event values can expose input-derived operational data if an API serializes them. Current change does not publish a new route; existing SPAJA result consumers will see extra events and should enforce their own redaction/auth policies. Next fallback phase needs policy for previously imported working state, failure status and graph budgets. Human review required; rollback reverts event fields and stale-cache fix, but would restore previous stale-result risk. No dependencies/config/workflows or autonomous operations.
